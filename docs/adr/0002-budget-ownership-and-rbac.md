# 0002. Budget ownership and RBAC

- Status: Accepted
- Date: 2026-10-04

## Context

The HLD says teams "see and own their budget through Kubernetes RBAC and GitOps". If owning includes editing,
a team that goes over budget can raise `maxActiveSeries` or set `mode: Observe`, and the budget no longer
protects the shared Prometheus. The design must say who is allowed to write a CardinalityBudget.

## Options considered

1. **Platform owns, teams read.** The platform team writes budgets (for example from a platform Git repo).
   Teams get `get`/`list`/`watch` only. Simple, standard RBAC; budget changes go through the platform team.
2. **Teams edit within limits.** Teams may edit, and a ValidatingAdmissionPolicy (CEL, built into Kubernetes,
   no webhook) rejects values above a platform-set ceiling. Self-service, but needs a place to store the
   ceiling and more to install and test.
3. **Split objects.** A cluster-scoped object sets ceilings; teams tune below them. This is
   `ClusterCardinalityBudget`, already scoped to V2.
4. **Teams fully own.** No protection; rejected.

## Decision

Option 1 for V1.

- Only the platform team creates and edits CardinalityBudget objects. This covers every field, including
  `mode` and `enforcement.protectedMetrics`.
- Teams get read-only access through the viewer ClusterRole generated by Kubebuilder
  (`cardinalitybudget-viewer-role`), bound per namespace.
- The install docs ship an example RoleBinding for teams and state the ownership model.

## Consequences

- No team-editable fields exist in V1; no admission policy is needed for v0.x.
- Option 2 can be added later as extra YAML in the Helm chart without an API change.
- Teams request changes (for example a protected metric) from the platform team.
